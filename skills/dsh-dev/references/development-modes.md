# MVP、敏捷迭代与可维护性

这些是委托开发的工作方式，不是 dsh 新增 CLI、插件或运行模式。只在用户明确要求使用 dsh 开发时执行；维护 skill、只打开和非项目消息不进入本流程。项目、权限、去重、文件职责、预算及恢复仍按原规则；模式选择不授权发布或操作其他账户。

## MVP

MVP 是 Minimum Viable Product（最小可行产品）。用户要求 MVP 或先验证核心需求时采用，以最少产品范围验证最重要的用户需求与价值。

1. 用户已给出核心需求就保留它；否则从目标用户、要解决的问题、一次使用应产生的结果推导最重要的流程。说明哪些是用户要求、哪些是推断。影响产品核心或能否验证的歧义先澄清，其余采用合理默认值；不要把“最容易做的功能”当作核心需求。
2. 将范围分为本轮核心与明确延后项，给核心流程具体输入、动作、结果及关键错误边界，沿用验收编号。优先做一条从入口到结果可实际运行的流程，而非许多互不连通的页面。未纳入核心的润色、扩展功能和规模优化不阻塞 MVP；不能删掉用户已明确的核心条件来缩小范围。
3. 给 dsh 当前核心、延后项、允许文件、验收和预算，要求最简单的可维护实现。MVP 允许功能范围小、界面朴素、已披露的临时实现；不允许以占位按钮、固定返回值或假数据冒充核心功能。mock/内存存储/手工步骤是否可用取决于验证目标，采用时在演示和交付中明确标出；如果用户要求真实支付或重启后仍保留数据，它们不能代替该核心行为。
4. 要求最少可运行说明和可复现演示；Codex 独立跑核心完整流程及相关错误边界，核查真实结果和采用的替代依赖。核心通过后交付已实现范围、延后项、临时取舍和已知限制，不擅自扩成完整产品。关键项失败/未验证不能叫作已完成的 MVP；代码验收通过也不等于市场需求或商业价值已被验证。用户另要求敏捷时按下面逐轮交付。

例如“课程报名 MVP”的用户核心是提交报名并在重启后查看结果：本轮做录入→校验→持久保存→列表查询；美化和营销功能可延后，内存列表不能满足已明确的持久化要求。这是范围示例，不是替用户默认选择技术栈。

## 敏捷迭代

仅用户要求敏捷或逐轮审查时启用；普通开发和长任务里程碑不自动增加用户审批。

- 建立简短、可调整的待办，按用户价值和依赖挑本轮小范围；每轮交付可演示增量。串行依赖先完成，不强制固定周期、固定轮数、多 Agent、worktree 或插件。用户已有迭代范围优先。
- 轮次可记为 I1、I2…；每轮沿用目标验收编号，记录本轮范围、完成依据、剩余预算和下轮候选。新反馈更新待办与验收，旧编号不复用为不同要求，改变已确认目标要说明影响。
- **每轮顺序：dsh 实现 → dsh 自审并修复 → Codex 独立核验 → 用户审查。** 提示词要求 dsh 自审实际 diff/新文件、核心逻辑、边界、测试、可维护性和越界，给具体问题、修复及检查结果；全部写入者停写后才交验收。没有自审证据先补该阶段，不能把一句“已自审”当作证据。
- Codex 自行检查实际文件与必要测试/界面，区分 dsh 自审线索与独立证据；失败项在本轮定点修正并重审、复验，保留已通过行为和用户修改。不用“dsh 自审通过”替代独立验收，也不用用户说“可以”掩盖已知关键失败。
- 给用户本轮可运行成果/演示方式、逐项结果、自审发现及处理、独立核验、取舍和未验证项，再请用户审查本轮并给通过/修改/停止的反馈。将状态标为 **等待用户审查**，停止新增实现与下一轮提交；不因超时、沉默、旧轮批准或已计划下一轮就推定本轮通过。用户回复到来后按实际反馈继续，明确停止则保存必要摘要并结束。等待审查不保留后台写入者，不承诺结束对话后自动继续。
- 用户通过本轮可进入下一轮，用户调整目标就重新选择下一增量；全部当前验收满足且最终一轮获用户确认后才报告敏捷任务完成。在已展示本轮成果和核验证据的上下文中，用户明确回复“通过，继续下一轮”即可按反馈推进，无需重复确认；未展示成果时的泛泛“继续”不能替代本轮审查。预算和原停止条件仍优先，不为完成轮数无限返工。

## 默认可维护性要求

每个开发任务（含 MVP 和敏捷）默认把下面要求缩成适合项目的几句话写入 dsh 契约，并在自审/独立验收中检查；它不是所有常量都禁止的口号。

- 先识别当前实际变化点，例如价格规则、可选课程、外部接口或存储方式；复用项目现有组织方式。稳定的业务逻辑与 UI、存储、网络等容易变化的边界分开，模块职责和接口清晰，避免同一业务规则在多个位置重复。
- 运行环境、服务地址、可变业务参数在合适的配置/参数/集中规则入口管理，避免写死私人绝对路径、凭据或散落的费率/名单。合理默认值、算法常量和测试样例可保留，命名或解释其意义；不为一个常量强造配置系统。
- 优先少量明确函数/模块和直接实现，保留兼容接口与项目习惯；没有具体变化依据不建设通用插件框架、层层抽象或大范围重构。MVP 缩减非核心范围也保留基本职责边界，避免以“临时代码”为理由复制大量规则。
- 从当前需求或用户给出的未来方向选择一个有意义的变化探针，例如修改配置中的课程名/费率后核心流程仍正确，或替换一个外部适配器而不改核心逻辑。按风险用现有测试、临时配置或代码检查验证修改应集中在哪里，报告实际修改点与结果；没有合理探针就检查变化边界并说明，不为未知未来写测试。
- 检查可读性、重复规则、错误处理及核心回归，并说明有依据的临时取舍。目标是让已知或合理预期的变化影响局部；无法保证代码永远不改、覆盖任意未来需求，不能宣称“以不变应万变”已被证明。用户明确要求一次性原型或限制结构时按其目标做最小实现，并披露维护代价。

## 提示词骨架

按实际模式取需要的字段，不强制每次产生新文件：

```text
模式：普通开发 / MVP / 敏捷 / MVP + 敏捷。
核心结果与依据：用户给出的要求；推断及待澄清的核心歧义。
本轮：I1（仅敏捷），产物与允许范围；明确延后项。
验收：A1…；核心全流程、相关错误边界、变化探针（有实际依据时）。
维护：遵循现有结构，集中可变规则/配置，分离实际变化边界，避免过度抽象。
审查：敏捷要求完成自审和必要修复，列出证据，然后停写等待 Codex 独立核验及用户审查。
预算、实际会话设置、文件职责与交接：沿用任务契约。
```
